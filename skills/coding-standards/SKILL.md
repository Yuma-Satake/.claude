# コーディング規約

## coding.mdの確認

`.claude/rules/coding.md`に記載されたコーディング規約は全ての原則の基本となるので、必ず確認すること

## プロジェクト固有の規約の確認

コードを編集・レビューする前に、対象リポジトリ内に`CLAUDE.md`や`.claude/rules/`配下のファイルなど、プロジェクト固有の規約が存在しないか確認すること。存在する場合は、このskillの内容に加えてそれらの内容も参照に入れ、両者を踏まえて実装・レビューを行う

## スコープ管理

- 与えたタスクに関連のない箇所の変更を行うことを禁止する。代わりにそれはユーザに報告する（例: 検索中に発見した別のバグやタイポなど）
- 一時的な検証用コード（デバッグ出力、ログ埋め込みなど）を仕込んだ場合、検証が終わったら直後に削除する。残したまま別の編集を続けると、その箇所を前提とした後続の変更が齟齬を起こす
- レビュー指摘や規約違反の修正を依頼された際は、指摘された箇所だけを直して終わらせず、同じ違反が別の表現で存在していないかを差分全体に対して検索すること。指摘者が挙げるのは代表例であることが多い。検索は指摘された文言そのものではなく、その規約が禁じている概念を表す語を列挙した正規表現で行う
- `git diff --stat`等で変更範囲を確認し、対象ディレクトリ・対象モジュール外への変更が広範囲に及んでいないか確認すること
- 既存機能の修正（エラー型変更・リファクタリング等）が新機能実装の差分に混在している場合、独立してコミット・レビューできるなら別PRへの切り出しを提案する

## 命名

- 変数名は、その値が実際に表す型・ドメイン上の役割を反映すること。「today」のような一時的・相対的な意味だけの名前は避け、「recordDayKey」のように扱っている値そのものの意味を表す名前にする
- 特に、後続処理で別の文脈（期間計算・比較など）にも使い回される値は、その場限りの文脈に依存した名前ではなく、値の意味を普遍的に表す名前にすること
- 関数・メソッド名は戻り値の意味だけでなく、呼び出し元が呼び出し前に把握すべき重要な副作用（永続化への書き込み・外部状態の更新など）も反映すること。読み込みのみを示す動詞（`load`/`get`等）だけでは副作用が隠れてしまう場合、副作用を示す語を組み合わせること
- 命名は、その変数や関数がどんな文脈で使われるかを読み取り、その文脈に見合った情報量を持つ名前にすること

## 既存コードとの整合性

- 実装にあたっては、既存コードとの整合性を重視し、既存に同様の実装がある場合にはそれらに倣って実装を行うこと
- データアクセス層で生SQLやテーブル名・カラム名を文字列としてベタ書きしないこと。ORM・クエリビルダ・生成モデル・定数など、プロジェクトの既存の方式を使う
- 共通関数やユーティリティを使用する際、該当箇所のニーズを満たすために、無理に共通関数を拡張して使用することは避ける（例: 本来の責務と異なるオプションを追加する/汎用関数の内部ロジックを安易に変更する）
- 関数や型ファイルを追加/更新する際には、DRY原則を意識し、同様の機能を持つ関数などが既に存在しないかコードベースを検索し、必要に応じてそれらを再利用/更新対象にすること
- DIコンテナ・クライアント（Dependency Injection用のインターフェース）に新しいメソッドを追加する前に、既に公開されている純粋関数を呼び出し元で直接組み合わせることで実現できないか検討すること。モック対象のインターフェースを不必要に増やさない

## 関数設計

- 関数は可能な限り純粋関数として実装し、副作用を伴う処理は丁寧に分離すること（例: 関数内で外部に依存する処理などを記述しないこと）
- 早期リターンを使用して、分岐のネストは浅く保つこと
- 欠落時の補完・フォールバック・デフォルト適用など、呼び出し元が把握すべき分岐はヘルパー内部に隠さないこと。分岐そのものはメインの処理フローに書き、ヘルパーは値の取得や変換など単一の責務に留める
- ヘルパー関数を「適用するかどうか」自体の判定（対象データの有無・前提条件の成立など、呼び出し元が意味を理解できる条件）も、関数内部の早期returnに隠さず、呼び出し元で判定してから条件付きで呼び出すこと。ヘルパーは名前が示す処理を無条件に実行する単一の責務に留め、「適用しない」という経路を関数内に持たせない。呼び出し元を見るだけで、いつその処理が実行されるかが分かる状態にする
- 非同期処理を書く際、依存関係のない処理を不必要に直列待機させていないか確認する（例: 無関係な非同期呼び出しの完了を待ってから別の非同期呼び出しを開始してしまっていないか）
- 実行時条件（オプション引数の有無など）によって処理の実装がほぼ丸ごと入れ替わる場合は、if/elseで分岐したまま1つの関数の内部に残さず、経路ごとに独立した名前の関数へ分離すること。元の関数は経路を選ぶだけのディスパッチャに留める。経路をまたいで使う処理（共通の判断・共通のロジック）は分離後も共有ヘルパーとして残し、経路固有の実装だけを分離対象にする。分離しないと、一方の経路を読む際に無関係な他方の経路の実装を読み飛ばす負荷が生まれ、経路名が関数名として明示されないぶん各経路の境界も読み手が都度たどり直す必要がある（早期リターンによる短いガード節は対象外。ここでの分岐は各分岐が独立した一連の処理を持つケースを指す）

## エラー・失敗シナリオへの対処

型としてエラーを表現する処理（Optional・Result・例外など）を扱う場合や、guard・assertion・fallbackの追加を検討する場合は、常に「その失敗が呼び出し時点の実行時の前提のもとで本当に発生しうるか」を先に判断し、結果に応じて対処を分けること。

- 実行時に発生し得ないと判断できる場合（型システムやAPIの都合でOptional/throwsとして存在するだけで、呼び出し時点の前提が保証されているもの）: 呼び出し元に選択の余地を与えず即座に処理を停止させること（例: Swiftの`fatalError`/`preconditionFailure`、Goの`panic`、TypeScriptでcatchせずに`throw`をそのまま伝播させるなど、言語の慣用的な即時停止手段を使う）。呼び出し元でのハンドリングやフォールバック処理を書かない
- 実行時に発生しうると判断できる場合（外部入出力の失敗、ユーザ入力・外部データの不整合など）: 呼び出し元が対処できるよう、エラーとしてスローする、または戻り値（Result型・Optional等、言語慣用の形）として返すこと。その場で握り潰したり、無条件にデフォルト値へフォールバックしないこと
- どちらに分類されるかは、エラーの型定義そのものではなく「その呼び出し文脈で実際に発生しうるか」という実行時の前提で判断する。同じエラー型・同じcaseであっても、呼び出し文脈によって分類が変わりうる（例: 「設定が未保存」を表すエラーは、設定前の画面では発生しうるエラーとして返し、設定完了後にのみ到達する画面では発生し得ないエラーとして即時停止させる）
- 特にOptionalやエラーを返すAPIに対してguard/assertionを追加する際は、そのAPIが実際にどの条件で失敗を返すか（ドキュメント・仕様）を先に確認し、防ぎたい失敗シナリオ（例: 外部設定の誤り）がその条件で本当に検知できるかを検証すること。検知できない場合はガードを追加せず、単純な`?? デフォルト値`等で済ませる
- コードレビューからの「推奨」指摘を採用する際も、この基準を必ず適用する。レビュー指摘だからといって無条件に防御的コードを追加しない
- ドメイン上は成立し得ない欠落が、APIの都合で Optional 等として型に現れている場合、デフォルト値で埋めて処理を継続しないこと。呼び出し時点の前提（例: オンボーディング完了後は設定が必ず存在する）に反する欠落は、黙って補完せずエラーとして表面化させる。デフォルト補完は「欠落が正当な状態」であるときに限る
- 「欠落が正当な状態」でデフォルト値を返す場合も、そのデフォルト値がドメイン上正常に発生しうる値と区別できないなら、コメントで意図を説明するだけでは呼び出し元は「欠落」と「正常な値」を見分けられない。呼び出し元が両者を型で判別できるよう、Optionalやenumなど区別可能な形で返すこと
- 外部ライブラリの関数がパラメータ（Calendar/Locale/Config等）に内部デフォルト値を持つ場合、呼び出し側で明示的に別の値（呼び出し元の環境依存値等）を渡す前に、そのライブラリのデフォルトが何を前提にしているかを確認すること。前提を確認せずに上書きすると、ライブラリ内部が想定する条件が崩れ、意図しない不具合を招く
- 永続化された値や、別プロセス・別時点で書かれた値を読み出す経路には、`precondition`・`fatalError` 等の即時停止を置かないこと。書き込んだのが自分自身のコードであっても、書き込み時と読み出し時でタイムゾーン・ロケール・アプリバージョン・スキーマが異なりうるため、「内部で書いた値だから不変条件は保証されている」とは言えない。読み出し経路では正規化して受け入れるか、値として扱えない場合は回復可能な結果（キャッシュミス扱い・再取得など）に落とすこと
- 「起こり得ないはずの不変条件違反」を検知するためだけに、専用のエラー型を新設したり、余分なデータ取得（本来1件でよいところを2件取得して重複を検出する等）を行わないこと。検知コストを払っても呼び出し元にできることが無いなら、その検査自体が不要である。不変条件は検査ではなく、不正な状態を作れない生成経路（検証付きの単一のイニシャライザ等）で担保する

## 変更時の影響確認

- ファイルの変更・削除を行う際には、ドキュメント内にそれらのファイルへの言及がないか、コードベースを検索し、必要に応じて更新すること
- 型・プロトコル・関数などの名称を複数ファイルに渡ってリネームする際は、全対象ファイルへの適用が完了した直後にビルド（またはコンパイルチェック）を実行し、適用漏れがないことを確認すること
- 関数・プロパティ・型などのシンボルをリネームする、またはアルゴリズムの挙動を変更する際も、ドキュメント内（コードブロックの引用・シーケンス図等）にそのシンボル名や挙動の記述が残っていないか検索し、必要に応じて更新すること。ビルドはコード側の参照漏れは検知するが、プローズで書かれたドキュメントの記述漏れは検知しない
- 内部関数の失敗時の挙動（スローする条件の追加、nilを返す条件の変更など）を変更する際は、その関数を呼び出す全ての箇所を洗い出すこと。特に、本来と異なる目的（例: 読み取り専用の関数を書き込み・自己回復処理から流用している）で内部的に再利用されていないか確認し、目的の異なる呼び出し元に同じ失敗許容度を適用してよいか個別に判断する。判断せず一律に適用すると、一方の呼び出し元の意図しない挙動変化（自己回復不能になる等）を見落とす
- 定数の値（リトライ間隔・取得件数・ウィンドウ幅・閾値など）を変更する際は、その定数の大きさを暗黙の前提にしている判定ロジックが他にないか確認すること。特に打ち切り条件・早期リターン・ヒューリスティックは、元の値では滅多に成立しなかった条件が、値を小さく（または大きく）した途端に日常的に成立するようになる。ビルドもテストも通り、結果が静かに劣化するだけなので検知されにくい
- 関数の戻り値の型・意味を変更する際（Optional化、新しいエラーケースの追加、値の意味の変更など）は、コンパイルが通ることの確認だけで済ませない。呼び出し元をたどり、その値がUIに表示される場合は、変更後の値（新たに増えたnil・エラーケース等）が実際にどう表示されるかまで確認すること。型システム上は正しくコンパイルできても、対応する表示分岐が無く画面が空白になる、既存の表示条件に引っかからず非表示になるといった見た目の劣化が見過ごされうる
- ドキュメントの一部（表・箇条書き・具体例）を更新する際は、差分箇所だけでなく同一ドキュメント内の前提文・要約文まで読み直し、矛盾が残っていないか確認すること。差分箇所だけを直すと、前提文と表・具体例の記述が食い違ったまま残る
- 固定値やpropとして渡していた挙動を、実行時のコンテキスト（ブラウザ履歴、キャッシュ、外部APIの状態など）に依存する挙動へ変更する際は、そのコンテキストが存在しない、または想定と異なる状態でその処理へ到達しうる経路（直リンク・共有・別クライアントからの流入など）を洗い出し、その経路でも成立するか確認すること

## 状態管理

- 他の状態から計算しえる状態は、計算式を使用して計算すること。状態として保持しない

## 可観測性（ログ設計）

- 外部API呼び出し・エラー発生箇所のログには、障害調査に必要な情報（呼び出し先の識別子・HTTPステータス・エラーコード等）を出力すること
- 機微情報（PII・認証情報・ユーザー入力値）をエラーメッセージやログに含めないこと
- 上流サービスから受け取ったエラーメッセージ本文をそのままログに出してよいかは上流サービスごとに異なる（PIIを含みうる）。プロジェクトにログ出力可否の方針があれば従い、無ければ出力前に確認する

## 定数の管理

- 基本的に処理における定数はインラインで記述せず、定数は適切なフォーマット（TSであれば`const XXX_XXX: XXX = XXX`）で定義し、ファイル内の先頭、もしくは定数ファイルを作成し定義すること（UIなどで表示するテキストは除く）
- 定数ファイルは`const.xx`なとどし、その関数内でしか使わない→ファイルの先頭/そのドメインに閉じている→そのドメインのルートに配置/プロジェクト全体で使う→共通定数ファイルに配置
