# issue-fix

引数: $ARGUMENTS

引数の解釈:

- issue番号: 引数中の最初の数値トークン。以下 `<issue番号>` と表記する
- `-a`: 自律モードで実行する（位置は問わない）
- 上記以外の文字列: ユーザからの追加指示としてプランニング・実装時に必ず考慮する

GitHub issue `<issue番号>` を修正する。`~/.claude/rules/` 配下のルールおよびプロジェクト固有の `CLAUDE.md` に従って実装する。EnterWorktreeで作成した独立したworktree内で作業し、現在の作業ディレクトリのブランチ・未コミットの変更に一切影響しない。

## 実行モード

**通常モード**（デフォルト）: アプローチ選択・Plan承認をAskUserQuestionでユーザに確認しながら進める。レビュー用skillの選定はモードに関わらず常にAIが自動で行い、選定結果をユーザに報告する（後述「Phase 1」参照）。

**自律モード**（`-a` 指定時）: プランニング・実装方針の決定に AskUserQuestion は用いず、AI が自ら判断して最後まで走らせる。ユーザ確認は以下の限定的なケースのみ許容する:

- issueが存在しない・不明瞭で修正内容が確定できない
- 既存のPRが存在し、そのまま継続するか新規作成か外部状態に依存する判断
- code-reviewerの指摘内容が根本的に矛盾しており、外部知識なしに判断不能
- 既に別のworktreeセッション内で作業しており、新規worktree作成のために現在のworktreeの終了（ExitWorktree）が必要な場合

これら以外は AI が自身の判断で決定し、判断根拠をログ（issueコメントや報告）に残すこと。

以降の手順で「通常モード:」「自律モード:」と記載のある箇所は、モードに応じて動作を切り替える。記載のない箇所は両モード共通。

## 作業環境

デフォルトでEnterWorktreeツールにより独立したworktreeを作成し、以降の全工程（実装・品質チェック・レビュー）をその中で完結させる。現在の作業ディレクトリの状態（ブランチ・未コミットの変更）に一切影響しない。

## コンテキスト管理（両モード共通）

このスキルは情報収集・往復確認・レビューサイクルを多用するため、メインセッションのコンテキストを圧迫しやすい。以下を徹底し、必要な情報だけを残す。

- **大きい/多数のファイル調査はサブエージェントに委譲する**: 数百行を超えるファイルや10ファイル以上の横断調査をメインコンテキストで直接Readしない。Explore/general-purposeエージェントに「静的モデル・動的モデル・結論」を要約させ、根拠として必要な引用のみメインに持ち帰る。実装直前に編集対象ファイルそのものを読むのは問題ない。
- **AskUserQuestionの選択肢はユーザに聞く前に軽く裏取りする**: 選択肢がissueやリポジトリの実情と合っていないと自由回答での往復が発生し、そのやり取り全体がコンテキストに積み上がる。質問を投げる前にリポジトリ内・issue内を一度軽く探索し、実情に即した選択肢に絞ることで往復回数を減らす。
- **要約(コンテキスト圧縮)後は差分だけ読み直す**: 会話が要約された後、要約に含まれる既読ファイルを無条件に再Readしない。要約の記述で判断できる場合はそれを信頼し、実際に編集する範囲や要約に含まれない新規箇所のみ読み直す。

## スコープ管理（両モード共通）

- 実装スコープは、issueの要件・受け入れ条件と、それらを成立させる直接依存だけに限定する
- 類似箇所の不具合、既存コードの整理、将来の拡張性、共通化できそうという理由だけでは変更対象に含めない
- 単一機能の対応では、その機能内に閉じる実装を優先する。共有化が直接必要な場合も、対象外の既存consumerを新しい共通処理へ移行したり、公開API・型・挙動を変更したりしない
- Planの変更ファイル一覧を実装差分の許可リストとして扱い、各ファイルを「要件対応」「直接依存」「テスト」のいずれかに分類できない場合は含めない
- 調査・実装・レビューで見つけた対象外の改善案は実装せず、別対応候補として完了報告へ記録する。記録目的だけのTODOや関連issue参照をプロダクトコードへ追加しない
- 動作確認専用のモック、seed、件数、設定変更は、issueの成果物として明示されていない限りコミット対象の差分へ残さない
- 実装後とレビュー修正後に変更ファイル一覧をPlanと照合する。Plan外の差分は、要件達成に不可欠な理由を確認してスコープへ追加するか、差分から除外する
- 通常モードでPlan外のファイルを追加する場合は実装前にAskUserQuestionで承認を得る。自律モードでは要件達成または今回の変更によるデグレード防止に不可欠な場合だけ追加し、理由を完了報告へ記録する

## 手順

### 1. ブランチ作成

- EnterWorktreeツールに `name: "issue-<issue番号>"` を指定して実行する
  - 同名のworktreeが既に存在する場合、EnterWorktreeが自動的にそのworktreeを再開する。未コミットの変更がなく、かつ未コミット状態またはPRマージ済み・リモートブランチ削除済みであればベースブランチの最新状態に巻き戻り、それ以外（コミット済みで作業継続中など）はそのままの状態で再開する
  - 現在のセッションが既に別のworktree内にある場合、新規worktreeの作成はできない。ExitWorktreeで現在のworktreeを終了するかどうかをユーザに確認する（自律モードでも例外として確認する）
- 作成されるブランチ名は `worktree-issue-<issue番号>` のようにツールが自動採番したものになるため、`git branch -m feature/issue-<issue番号>` でブランチ命名規約に沿った名前にリネームする（worktreeを再開した場合、既に `feature/issue-<issue番号>` にリネーム済みであればスキップする）
- worktreeは現在の作業ディレクトリと独立しているため、未コミットの変更の確認は不要

### 2. issueについての情報収集

**調査フェーズは必ずサブエージェントに移譲する**。メインコンテキストで `gh pr view` / `gh issue view` / WebSearch / WebFetch を直接実行しない。

- **サブエージェント**に、issue本文・コメントの精読、言及されているPR・issue（`#xxx` 形式）の内容確認、外部リンクの情報取得を依頼する
- 複数の情報源がある場合、可能な限り並列でサブエージェントを起動する
- メインコンテキストには「関連する既存の議論・決定事項・背景情報」の要約と、根拠として必要な引用のみを持ち帰る

### 3. コード/ライブラリについての情報収集

**調査フェーズは必ずサブエージェントに移譲する**。メインコンテキストで対象コードのRead/Grepを直接実行しない。

- **Exploreエージェント**を用いて、修正対象のコード・類似実装・呼び出し元・テストの有無を調査する
  - 影響範囲が広い場合は `thoroughness: very thorough`、限定的な場合は `quick` を指定する
  - 大きな設計資料・大量のファイルを精査する必要がある場合も、メインコンテキストで直接Readせずサブエージェントに要約させる（「コンテキスト管理」参照）
- ライブラリの仕様やバージョンに関わる情報が必要な場合は、**general-purposeエージェント**に公式ドキュメントの確認（WebSearch / WebFetch）と要約を依頼する
- プロジェクトの `CLAUDE.md` やルールファイル（`rules/`, `docs/` 配下）の確認も **Exploreエージェント** に依頼し、プロジェクト固有の規約を要約させる
- 変更予定ファイルに対して進行中の他PR（未マージ）が存在しないか `gh pr list --state open` や `git log --all --oneline -- <変更予定ファイル>` で確認する。issue本文に明記されていない並行作業でも、同じファイルを変更するPRが後からマージされるとブランチの起点を再度やり直す手戻りが生じる

調査結果は以下の2つの視点で整理する：
- **静的モデル**: 関係するコンポーネント・クラス・モジュールの責務と相互関係
- **動的モデル**: 修正対象の主要な処理フロー（データの流れ・呼び出し順序）

### 4. プランニング

**Phase 0: 背景の共有（両モード共通）**

ユーザはissue番号を見てClaudeに実装を委任しており、issue本文・コメントを読んでいない前提で進める。Phase 1のAskUserQuestionより前に、収集した情報を元に以下を**通常のテキスト出力**として提示する。

- 現状どうなっていて何が問題か（issueが指摘する事象を、issue内の略語・固有名詞をそのまま使わず意味を補って説明する）
- issueが求める状態（受け入れ条件を平易な言葉で）
- 検討したアプローチの候補と、次のPhase 1で確認する推奨方針・理由（候補が複数ある場合、棄却しそうな案があれば一行で触れる）

料理・車など無関係な分野への比喩は使わない。自律モードでもこの出力を行う。テキスト出力はユーザ承認を伴わないため自律モードの制約（AskUserQuestionを用いない）には触れない。

**Phase 1: 実装アプローチの選定**

1. 収集した情報を元に、実現可能な実装アプローチを **複数案** 検討する
   - 各案のトレードオフ（変更範囲・リスク・保守性・パフォーマンスへの影響など）を評価する
2. アプローチとレビュー用skillsを決定する
   - **レビュー用skillsには `coding-standards` を常に無条件で含める**。言語・フレームワーク・レイヤーを問わず適用される規約であるため、ユーザーに確認せず、モードや変更内容に関わらず必ず含める。
   - **レビュー用skillsには `coding-architecture` も原則含める**。ユーザーには確認せずAIが判断する。
     - 変更予定の差分が特定の単一層にとどまるなど、関心の分離・DRY原則の観点からどう見ても不要と判断できる場合に限り、含めないことができる。その場合は判断根拠をユーザに明示する（Plan提示時、または決定事項として言及する）
     - ドキュメントのみの変更であっても、設計・アーキテクチャに関する判断を伴うタイミング（設計ドキュメントの新規作成・変更など）では含める
   - **レビュー用skillsには `coding-regression` も常に無条件で含める**。要件網羅性・デグレの観点は変更差分のコードを読むだけでは検出できず、issueの受け入れ条件と既存動作の両面から検証が必要なため、モードや変更内容に関わらず必ず含める。
   - 上記3つ以外の追加skillsは、モードに関わらず常に **AI が自ら選定** する。変更ファイルの言語・フレームワーク・レイヤー・変更の性質（機能追加/バグ修正/リファクタ）から関連するskillsを推論する（例: React変更なら `coding-react-next`, TypeScript変更なら `coding-js-ts`）。ユーザには確認せず、決定したレビュー用skillの一覧と選定理由を通常のテキスト出力で報告する
   - 以下のAskUserQuestion・AI選定はアプローチ選択のみを指す
   - 通常モード: **AskUserQuestion** でアプローチ選択を確認する
     - 質問を投げる前に、選択肢がissue・リポジトリの実情に即しているか軽く裏取りする（「コンテキスト管理」参照)。的外れな選択肢は自由回答の往復を招き、コンテキストを余計に消費する
     - 複数案を選択肢として提示する（推奨案をデフォルト選択としてtrueにする）
   - 自律モード: 以下の基準で **AI が自ら選定** する
     - アプローチ選定基準: issueの要求を満たすこと / プロジェクトの既存規約・パターンと整合すること / 変更範囲・リスクが必要最小限であること / 保守性を損なわないこと

**Phase 2: 詳細タスクの展開**

3. 決定したアプローチを具体的な変更ファイル・タスクに分解する
   - 修正対象のスコープ（関連ファイル・影響範囲・テスト範囲）
   - エッジケース・デグレードリスクへの対応方針
   - 各変更ファイルが「要件対応」「直接依存」「テスト」のどれに該当するか
   - 調査で見つかったが今回実装しない「スコープ外として見送る項目」
4. 通常モード: Phase 2 Planを以下のフォーマットで**通常のテキスト出力として本文に表示**し、承認が得られるまで修正を繰り返す / 自律モード: ユーザ承認は不要、そのまま次へ進む
   - ユーザはPlanの元テキストファイルを直接見に行かないため、AskUserQuestionの選択肢や質問文にPlan本文を要約・埋め込みせず、必ず先にテキスト出力でPlan全文を表示してから、それとは別にAskUserQuestionで承認確認を行う
   - AskUserQuestionの質問文は「上記のPlanで実装を進めてよいか」程度の短い確認に留め、Plan内容の再掲・要約はしない

**Phase 2 Planの提示フォーマット**

- 冒頭に「背景」「方針」をPhase 0で共有した内容に基づき記載する。ユーザがissue本文を読んでいない前提で、比喩を使わず、issue内の略語・固有名詞は意味を補って書く。「背景」はPhase 0からの変化がなければ簡潔な再掲でよいが、「方針」はPhase 0時点の推奨案ではなく、Phase 1で確定したアプローチを記載する
- 「背景」「方針」に続けて変更ファイル一覧を **ディレクトリツリー形式** で列挙する（`├──` `└──` `│` を使用。ASCII版の `|--` は使わない）
  - ファイル数に関わらず常にtree形式にする（1ファイルでもフルパスを1行で書かず、ディレクトリとファイル名をtreeで分ける）
  - rootは対象ファイルを含むディレクトリにする。共通接頭辞が浅い/存在しない場合は複数rootを縦に並べてよい（無駄に浅い/深いネストを描かない）
  - 各葉（ファイル名）の末尾に種別（新規/編集/削除/移動）を付ける。移動の場合は移動元パスを添える
- ファイルごとに見出しを立てる。見出しはtreeの葉と対応させるため **プロジェクトルートからの相対パス** で書く
  - 変更点を **1箇条書き1変更** で言い切り形に書く。複数の変更を「〜し、〜する」と1文に連結しない
  - 理由・規約参照・TODOの中身などの補足は変更点と分け、「備考:」として書く
  - 移動を伴う場合は「移動元 → 移動先」の形で1行にまとめる
- 末尾に確認方法（ビルド・テスト実行など）を独立した箇条書きとして添える

5. 決定事項をissueにコメントで記録する
   - 「選択したアプローチ」「その根拠（ある場合のみ）」「検討した代替案（あれば）」「主要な変更箇所」を箇条書きで、言い切り形で記載する
   - 要約や説明文は不要
   - 複数回に分けず、Plan確定後に一度だけ投稿する

### 5. 実装

Planに沿って実装する。

- 追加指示があればその内容を反映する
- コミット・ステージング（`git add`等）はこのスキル内では行わない。ユーザから明示的な指示があるまで実行しない
- 並列実行可能な変更（独立ファイル編集・調査）は積極的に並列化する
- 共有処理を追加しても、要件対象外の既存画面や既存consumerへ適用範囲を広げない
- Plan外のファイルが必要になった場合、通常モードでは編集前にAskUserQuestionで承認を得る。自律モードでは直接必要性がある場合だけ編集し、理由を記録する
- 実装完了時に変更ファイル一覧をPlanの許可リストと照合し、説明できない差分を品質チェック前に除外する

### 6. 品質チェック

変更内容に応じて以下を実行し、エラーがないことを確認する。並列実行可能なものは並列で実行する。

- **type-check / lint**: プロジェクトのスクリプトを `package.json` / `pyproject.toml` / `Makefile` 等から検出して実行する（例: `npm run typecheck`, `npm run lint`, `pnpm check`, `yarn tsc --noEmit`）
- テスト: 変更箇所に関連するテストがあれば実行する
- スクリプトが不明な場合は `CLAUDE.md` や README を参照する
- エラー発生時は根本原因を特定して修正する。`--no-verify` やチェックのスキップで回避しない

### 7. レビュー

プランニングで決定したskillごとに**code-reviewer agentを1体ずつ並列起動**する（同一メッセージ内で複数Agent呼び出し）。code-reviewer agentは1体につき最大1 skillしかロードできないため、skillの数だけcode-reviewerを起動する。

各code-reviewerへの指示には以下を含める：
- レビューしてほしい変更ファイルと変更の概要
- 承認済みのスコープとPlanの変更ファイル一覧
- 要件達成に直接必要な問題と、既存コードの改善・共通化提案を分けて報告すること
- スコープ外の既存画面やconsumerへの変更拡大を提案しないこと
- 割り当てるskill名（code-reviewerがSkillツールでロードしてレビューに活用する。1体につき1 skillのみ）
- 今回並列起動する全code-reviewerへの割り当てskill名の一覧
- coding-regressionを割り当てる場合、対象issueの番号
- 「このスキルはレビュー時点でコミットを行わないため、新規追加ファイルがgit上で未add/未commitの状態であることは正常であり指摘不要」
- 「このタスクの調査・実行にあたって追加のエージェントを起動しないこと」

指摘への対応:

- すべてのcode-reviewerの結果を回収し、必須修正をマージする（同一指摘は重複排除）
- 修正が必要な指摘に対応し、再度 skill ごとに code-reviewer agent を並列起動して再レビューを依頼する
  - ある周で指摘が0件だったskillは、以降の周では起動対象から外す。指摘が残っている（または新たに対応が発生した）skillのみ再起動する
  - 再起動するcode-reviewerへの指示は、直前までのレビュー周・指摘内容・対応履歴（「前回指摘された〜を修正しました」等）を含めず、現在の差分のみを基準に初回レビューと同じ説明にする。過去の指摘に対応済みかどうかの確認はメインセッション側で指摘一覧と差分を照合して行う
- 修正を適用するたびに、Skillツールで `hunk-open` を必ず呼び出す
- レビュー指摘が既存コードの改善や別機能の変更を要求する場合、今回の差分が直接生じさせた不具合でなければ実装せず、別対応候補として扱う
- レビュー修正後に変更ファイル一覧をPlanと再照合する
- 指摘がなくなるまでレビュー→修正のサイクルを繰り返す
  - 例外: 必須修正が0件で、対応した推奨事項の変更が指摘内容と完全に一致する軽微な修正（命名変更など）である場合は、再レビューサイクルを省略し次工程へ進んでよい
- 通常モード: 指摘内容に疑問がある場合はユーザに判断を仰ぐ
- 自律モード: 指摘への対応・「対応不要」の判断は AI が自律的に行い、判断根拠を完了時報告に含める。指摘内容がプロジェクト規約に対して根本的に矛盾しており、外部知識なしに判断不能な場合のみユーザに判断を仰ぐ
- 自律モード: 無限ループ防止のため、レビューサイクルは最大5周までとする。5周終了時点で残った指摘は完了時報告に「未対応の指摘とその判断」として明記する

## 完了時の報告

報告前に、Skillツールで `hunk-open` を必ず呼び出す。

ユーザはissue本文を読まずに依頼していることが多い前提で、以下をこの順にユーザに報告する。比喩は使わず、issue内の略語・固有名詞は意味を補って説明する。通常モードでPhase 0・Phase 2 Planで既に共有済みの内容も、報告はそれ単体で読めるように背景から改めて書く。

- 背景: 現状どうなっていて何が問題だったか、issueが求めていた状態
- 方針: 選んだアプローチとその理由（自律モードは選定根拠を含める）
- 使用したレビュー用skill一覧とその選定理由
- 実装した変更の要点
- この変更でユーザから見て何が変わるか（変更前→変更後）
- 実行した品質チェックと結果
- レビューで指摘・対応した内容（自律モードで未対応があればその判断）
- worktreeのパスとブランチ名。ExitWorktreeはユーザから明示的な指示があるまで実行しない旨
