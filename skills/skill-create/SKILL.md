# skill-create

skill の新規作成・改善を行う際は、まず Skill ツールで `skill-creator:skill-creator`（Anthropic 公式プラグイン）をロードし、その手順（ドラフト作成 → テスト実行 → 評価 → 改善のループ）に従う。以下は公式の手順に対する、このユーザー環境での個別ナレッジ。

## 設計方針

- `~/.claude/rules/` および `.claude/rules/` のfrontmatterで公式にサポートされるフィールドは `paths`（glob配列。マッチするファイルを読んだ際にロードされる）のみで、`description` 等の任意フィールドは存在しない（`paths` 未指定のルールは毎セッション無条件ロードされる）。rule側で「どんな時に読み込むか」を柔軟に制御したい・詳細な説明を持たせたい場合はrulesではなくskillへの切り出しを検討する
- 1スキル = 1責務とする。スキルの1ステップが独立した関心事に育って肥大化してきたら、別スキルに切り出し、呼び出し元には「Skill ツールで必ず呼び出す」と明記した参照だけを残す（例: commit スキルから knowledge-review スキルを呼ぶ構成）
- スキル名は目的が名前から分かる名詞ベースで付ける（例: knowledge-review、skill-create）
- 個人・プロジェクトスキル（`~/.claude/skills/`・`.claude/skills/`配下）をリネームする場合、呼び出しコマンド名（`/skill-name`）はディレクトリ名で決まり、frontmatterの`name`フィールドは一覧表示名にのみ影響する（プラグインスキルは例外で`name`が末尾セグメントを決める）。呼び出し名を変える場合は`git mv`でディレクトリ名を変更し、表示の一貫性のためfrontmatterの`name`・本文中の見出しや自己言及も合わせて更新する
- スキルディレクトリが外部リポジトリへのシンボリックリンクである場合、呼び出し名はリンク名のみで決まる。リンク先（別リポジトリ）のfrontmatter `name`まで書き換えるかは別リポジトリへの変更を伴うため、リンク名のみ変更するか、リンク先も含めて表示名を統一するかをユーザーに確認する

## 出力フォーマット設計

- ユーザーが「常に分かるようにしてほしい」等、常時性・網羅性を求める要件を出した場合、簡潔性を理由にした省略条件（件数閾値など）を自己判断で追加しない
- まず要件をそのまま満たす案（常に表示する等）を採用する
- 省略条件を入れたい場合は、それによって元の要件が損なわれないかを自問し、判断に迷うならAskUserQuestionでユーザーに確認する
- この「常時性を求める要件をそのまま満たす」原則は出力フォーマット以外の設計にも適用される。特にAskUserQuestionで項目を選択させる設計において、ユーザーが「常に◯◯する」「デフォルトで使う」と要望した場合、対象項目を選択肢に残したままデフォルト選択（true）にするだけでは「使うか毎回確認している」ことに変わりなく要件を満たさない。真に無条件適用を意味する場合は、その項目を選択肢自体から除外し、確認ロジックの外側で常に適用されるよう設計する

## コンテキスト分離の設計

- 収集系・調査系スキル（issue/PR読み込み、リサーチなど）で、収集した生データ（本文・差分・大量のコメント等）をメインの会話コンテキストに残したくない場合は、frontmatterに `context: fork` を指定する。スキル本文がそのままサブエージェントへのプロンプトになり、呼び出し元の会話履歴は参照できない独立コンテキストで実行され、最終報告のみがメインに返る
- `context: fork` を使う場合、スキル本文は「参照ガイドライン」ではなく「具体的なタスク指示」でなければならない（ガイドラインだけだとサブエージェントに実行可能な指示が渡らず、意味のある出力なしに終わる）
- `agent` フィールド（`context: fork` 時にサブエージェントの種別を指定）は省略可能で、省略時はデフォルトのエージェント種別（全ツール利用可）でフォークされる。読み取り専用に絞りたい・ツール構成を明示したいなど具体的な制約理由がある場合のみ指定し、なければ省略する
- skillのfrontmatterにmodelフィールドは存在しない。`context: fork`時にサブエージェントを特定モデル（例: haiku）で動かしたい場合は、そのモデルを`model`に設定した専用のagent定義（`~/.claude/agents/<name>.md`）を作成し、`agent`フィールドでそれを指定する
- `context: fork`（スキルfrontmatter）と、Agentツールの`subagent_type: "fork"`は名前が同じだが正反対の性質を持つ。前者は新規の独立コンテキストで開始し呼び出し元の会話履歴を持たない。後者は会話全体を継承した上でバックグラウンド実行され、そのツール呼び出しだけがメインの会話から隠れる。「会話履歴を引き継いだままメインコンテキストを汚さない」設計が必要な場合は後者（`subagent_type: "fork"`。有効化には`CLAUDE_CODE_FORK_SUBAGENT=1`が必要）を使う

## 動的コンテキスト注入

- スキル本文中の `` !`command` `` は、スキル内容がClaudeへ渡される前にコマンドを実行し、その標準出力でプレースホルダを置換する。Claudeが受け取るのはコマンドではなく展開済みの結果である
- 呼び出し時点で必ず必要になる、小さく決定的な読み取り専用データの注入に使う。現在のリポジトリルート・ブランチ・変更ファイル一覧・issueメタデータ・ライブレビューコメントなどが該当する
- コマンドの選択が先行する推論結果に依存する場合、失敗時に分岐やリカバリが必要な場合、取得が任意の場合、出力が大きくなりうる場合は注入せず、スキルの手順内でBashツールを明示的に呼び出す
- 注入コマンドはClaudeの判断前に実行されるため、原則として副作用を持たせない。差分・ログ・コメントなどはJSONフィールド選択、パス指定、件数制限などで出力を絞る
- プレースホルダは行頭または空白の直後に置く。``KEY=!`command` `` のように直前が文字の場合は展開されない。複数行のコマンドは開始フェンスを ` ```! ` としたコードブロックを使う
- 展開は元ファイルに対して1回だけ行われ、コマンド出力に含まれる別のプレースホルダは再展開されない
- `context: fork` と併用すると、展開済みのデータが独立コンテキストへ渡る。親会話を参照できない収集・調査スキルに、必要なライブデータだけを渡す用途に適する
- `allowed-tools` はプレースホルダの前処理には不要である。展開後にClaude自身がBashを呼ぶ必要がある場合だけ、必要最小限のコマンドを許可する
- `disableSkillShellExecution: true` の環境では、ユーザー・プロジェクト・プラグイン・追加ディレクトリ由来の注入は実行されず、無効化を示す文字列に置換される。無効化環境でも動作必須なら、明示的なツール呼び出しによる代替経路か、処理不能を示す分岐を設計する

## 評価・改善の進め方

- スキルの改善は評価駆動で行う。改善したい挙動と防ぎたい挙動をアサーションとして明文化し、旧版（スナップショット）と改善版をサブエージェントで並列実行して比較する
- 会話全体を対象とするスキル（振り返り・レビュー系）は、シグナルを埋め込んだ模擬会話トランスクリプトと模擬設定ディレクトリ（mock の rules・skills・プロジェクト）を用意すれば定量評価できる。ユーザー確認が必要なステップは、サブエージェントには提案書ファイルへの書き出しで代替させる
- 評価用ワークスペースは scratchpad に置く。公式 skill-creator は「スキルディレクトリの隣に置く」と指示するが、~/.claude は git リポジトリのため評価成果物で汚さない
- 評価のサブエージェントは、そのスキルが実際に動くモデルで実行する（例: model: sonnet のスキルなら評価も sonnet で行う）
- サブエージェントの並列駆動は agent-use スキルの原則に従う（成果物ファイル名に analysis・report 系を避ける点に注意）
