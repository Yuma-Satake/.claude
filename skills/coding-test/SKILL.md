# テスト コーディング規約

## 適用範囲

- テストコードの新規作成・編集・レビュー時に使用する

## タイマーとグローバルAPIのスタブ

- `IntersectionObserver` 等のグローバルなブラウザAPIをスタブするテストでは、実タイマー（`setTimeout` 等）に依存せず、テストフレームワークが提供するフェイクタイマー機能を使うこと。実タイマー＋ポーリングによる待機を併用すると、単体実行では成功してもフルテストスイートの並列実行下でスレッド競合によりタイミングが乱れ、まれに失敗する（flaky）ことがある

## テストの検知能力

- エラー型・分岐・条件式を変更した際は、既存テストのケース名や期待値が変更後の実装と一致しているか確認すること。ケース名が示すエラー型・分岐と、モック・スタブが実際に返す型・期待値が食い違っていないか確認する。変更前の振る舞いを前提にしたケース名・期待値が古いまま残っていると、実装が壊れてもテストが検知できない
- テストが本当にバグを検知できるかは、コードを読んで「検知できるはず」と推論するだけでは確信できない場合がある（期待値が偶然、正しい経路と壊れた経路の両方で同じ値になってしまうケースなど）。判断がつかない場合は、テスト対象のロジック（判定条件・変換処理など）を一時的に無効化・簡略化（例: 早期 return を入れる、条件式を固定値に変える）し、そのテストのアサーションが実際に fail する（red になる）ことを確認してから元に戻す。fail しない場合はテストの検知能力が不足しているので、アサーションを強化する（呼び出し引数の検証を追加する、複数の中間状態を確認する等）

## 不要なテストを追加しない

- テストの目的は、既存の振る舞い（資産）を将来の変更が壊したときに検知することであり、今回書いた実装がその場で意図通りに書けているかを確認するための自己検証ではない。「今回の変更が正しいか」を確認する目的だけで追加したテストは、将来別の変更がその内容を変えても誰も困らないなら、テストスイートに残す価値がない。テストを追加する前に「これは将来の回帰を検知するためのものか、それとも今回の実装作業を検証するためだけのものか」を区別すること
