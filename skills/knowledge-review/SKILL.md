# knowledge-review

会話の最初から現在までを振り返り、再利用可能な知見を抽出して適切な場所への反映を提案する。ファイルを先に眺めて「該当がないか探す」のではなく、必ず会話の振り返りから始めること。

Step 1からStep 4までメインセッションで実行する。サブエージェントは呼び出し元の会話履歴を継承しないため、会話全体を対象とするStep 1・Step 2を委譲しない。

## Step 0: 保留フラグを解除する

git commit後にknowledge-reviewの実行を促すリマインダーは、`~/.claude/hooks/set-knowledge-review-flag.sh`（PostToolUseフック、git commit成立時に発火）と`~/.claude/hooks/check-knowledge-review-pending.sh`（Stopフック）で実装されている。このskillを呼び出したら、対象リポジトリのフラグを明示的に解除する。

```
~/.claude/hooks/knowledge-review-flag.sh clear "$(git rev-parse --show-toplevel)" "${CLAUDE_SESSION_ID}"
```

gitリポジトリ外（`git rev-parse --show-toplevel`が失敗する場所）で呼び出された場合はこの手順をスキップし、そのままStep 1へ進む。

## Step 1: 知見候補の全列挙

この段階では汎用性を判断せず、機械的に拾い上げることに専念する。以下のシグナルごとに該当の有無を1つずつ明示し（該当がない場合も「該当なし」と記す）、該当する出来事を列挙する。

1. ユーザーから受けた指摘・修正・却下（特に同種の指示を2回以上受けたもの）
2. ユーザーが表明した新しい指示・好み（「今後は〜して」のような将来に向けた要望を含む）
3. コマンドやツールの実行が失敗し、別のやり方でリトライした箇所
4. skill の手順どおりに進めて詰まった箇所、手順に書かれていない判断を自分で行った箇所
5. 事前に知っていれば手戻りを防げた発見（環境・ツール・ライブラリの仕様など）
6. 期待した結果と実際の結果が食い違い、原因調査が必要になった箇所
7. うまく機能した工夫・手順で、次回も再現する価値があるもの
8. ユーザーが命名・言い回し・デザインなどについて指摘や誤りの訂正ではなく好みの調整を複数回にわたり繰り返し、最終的な結論に至ったやり取り（結論そのものだけでなく、調整の過程でユーザーが示した判断基準・優先順位に注目する）

各候補は「何が起きたか」「そこから得られる教訓」の1〜2行で書き出す。全シグナルが該当なしの場合はこのスキルを終了する。

## Step 2: 汎用性の判定と反映先の振り分け

各候補に対して次の判定を順に適用する。rulesは`paths`指定がなければCLAUDE.mdと同じく毎セッション無条件でロードされ続け、無関係な作業であっても行数分のコンテキストコストを永続的に払う。skill本体は呼び出されない限り読み込まれずコンテキストコストは低いが、追加すればその後も内容の正しさを保守し続ける責任が生じる。この判定は「間違っていないか」だけでなく「このコストを払う価値が本当にあるか」を厳しく問うためのものであり、機械的に拾ったStep 1の候補の大半がここで反映対象から外れるのが正常な結果である。

1. 再発性の判定: 次のいずれかに該当する場合のみ次の判定に進めてよい
   - 既存の rules・skills の記述どおりに従ったにもかかわらず失敗した（instruction failure。既存の記述自体に不備があるため、再発を待たず初回から対象とする）
   - 会話や記憶にある限り、同種の状況が複数回発生している（同じ間違いを2回目以降犯した、前回のセッションでも同じ訂正・確認を今回と同様に行った等）
   一度きりの指摘・訂正（既存の記述に問題がなく、他のセッションや過去の記録でも再発が確認できないもの）や、今回のセッション固有の外部要因（他セッション・他worktreeとの偶発的な並行作業、その日固有の環境の一時的な不調など）に既存記述に反することなく即興で対応できた事象は反映しない
2. 反映価値の判定: 「次回以降の作業でこの記述を読んだとき、行動が変わるか」で判断する。既に解決済みの個別事象の詳細（修正したバグの原因、そのとき限りの調査結果など）は、記録しても次回の行動を変えないため反映しない。同じ手戻りが再発しうる知見のみ次の判定に進める
3. 既知の判定: 反映先の候補（ユーザーレベルの rules・skills、対象プロジェクトの CLAUDE.md や `.claude/rules/` 配下）に同じ内容が既に正しく書かれているなら反映しない。既に書かれているが記述が不正確・不足している場合は「既存記述の修正候補」として次の判定に進む
   - 既存の rules・skills の記述どおりに作業して失敗した場合は、特に重要な修正候補として扱う。記述が「常に成り立つ」と断定していて、実際には環境やプロジェクトによって結果が異なると判明したなら、断定を確認手順や条件分岐に置き換える修正を汎用候補として挙げる（例: 「事前ビルドは不要」という断定 → 「デプロイスクリプトにビルドが含まれるか確認し、含まれない場合は先にビルドする」）。プロジェクト側への例外注記だけで済ませると、別のプロジェクトで同じ失敗が再発する
4. 汎用性・頻度の判定: 次の2軸で判定する
   - 汎用性（ポータビリティ）: 別のリポジトリ・別のプロジェクトで同じ作業をしても、この知見がそのまま成立するか
     - 特定のプロジェクト名・社内サービス名・リポジトリ内のファイルパスなどの固有名詞を使わないと教訓を記述できないならプロジェクト固有
     - 固有名詞なしで書ける場合でも、組織・チーム固有の運用ルール（コミットメッセージへのチケットID付与など）はプロジェクト固有として扱う
     - ツールに関する知見は「ツール自体の一般的な性質」（例: git stash は untracked ファイルを対象にしない）なら汎用、「そのプロジェクトでのツールの運用」（例: このリポジトリでは pnpm を使う）ならプロジェクト固有
     - 迷った場合は「6ヶ月後に無関係なプロジェクトでこの記述を読んで役に立つか」で判断し、それでも迷うならプロジェクト固有として扱う
   - 頻度・重大度: 汎用性の基準を満たしていても、次のいずれにも該当しない候補（＝滅多に発生せず、発生しても被害が小さい「エッジケース」）は反映しない
     - 今後も同種の作業で繰り返し遭遇しうる（低頻度ではない）
     - 発生頻度は低いが、遭遇した際の被害・手戻りが大きい（データ損失、本番障害、セキュリティ、長時間の手戻りなど）
     - 例1（反映しない）: 特定バージョンのツールでだけ起きた表示上の不具合を回避した、というような知見は汎用的に書けても再発頻度が低く被害も軽微
     - 例2（反映する）: 「git stash はuntrackedファイルを対象にしない」という仕様は、stashを使う限り常に関わり誤用時の被害（変更の消失）も大きい
5. 抽象化の検討: プロジェクト固有と判定した候補についても、一段抽象化すると汎用的な教訓にならないかを検討する（例: 「このリポジトリは pnpm を使う」という固有の知見 → 「パッケージを追加する前に lockfile の種類でパッケージマネージャを確認する」という汎用の手順）。抽出できた教訓は独立した候補として追加し、判定1から同じようにかけ直す。プロジェクト固有の失敗は汎用手順の確認不足を露呈していることが多く、固有の知見をプロジェクトに記録するだけではその改善機会を逃す
6. 反映先の決定: 汎用と判定した候補は、内容の性質で以下から選ぶ（上から順に検討し、最初に該当したものを採用する）
   - 複数ステップの手順・ワークフロー（リリース手順、特定観点のレビュー項目一覧、調査の進め方など）: 該当する `~/.claude/skills/` のスキル。手順が長い・特定の観点に限定される場合はSKILL.md本文ではなく `references/` 配下の個別ファイルに反映することも検討する（既存の分割方針に倣う）。既存スキルに適切な反映先がなければ、新規スキル作成を検討する。新設する場合は `~/.claude/skills/` 配下の既存スキルのディレクトリ構成・命名規則（ケバブケースの名称、`SKILL.md` のfrontmatter形式など）に倣う
   - 1行〜数行で書ける「常に◯◯する／◯◯は避ける」という短い事実・制約で、作業全般に関わるもの: `~/.claude/rules/`（適切なファイルがなければ新規作成を提案する）。この単純な事実・制約と、上記の複数ステップの手順の違いが、rule/skillのどちらに反映すべきかを分ける基準になる
   - 同種の短い事実・制約だが、特定のファイルパス・ディレクトリ（特定言語のコード、特定ディレクトリ配下など）にのみ関係するもの: 同じ `~/.claude/rules/` のファイルに、frontmatterで`paths`（globパターン）を指定したスコープ付きruleとして反映する。対象パスにマッチするファイルを読んだときだけロードされ、無関係な作業ではコンテキストを消費しない
   - すでにruleまたはskillに明文化されているにもかかわらず、絶対に守られるべき制約が繰り返し破られている場合（判定3のinstruction failureが再発している場合）: prompt指示の追記・強調ではなく、`hook-create` スキルを使ったhook化（`PreToolUse`での拒否など）を提案する。「必ず」「絶対に」という確実性を要求する制約は、指示ベースのrule・skillでは原理的に保証できない
   - 特定のagentのペルソナ・振る舞い・出力フォーマットに関するもの: `~/.claude/agents/<name>.md`（またはプロジェクトの `.claude/agents/<name>.md`）本体
   - プロジェクト固有: 対象プロジェクトの既存instructionファイル。適切なファイルがなければCLAUDE.md、`.claude/rules/<name>.md`（パス限定が必要な場合）の順で新規作成を検討する。ユーザーレベルには入れない。ただしチームで共有すべき規約か、自分個人の好み・環境固有の設定（サンドボックスURL、個人的なテスト用データなど）かを区別し、後者は共有される`CLAUDE.md`ではなく`CLAUDE.local.md`に反映する
   - 作業対象が `~/.claude` 自体である場合は、rules・skills・agents本体への反映として扱う

## Step 3: ユーザー確認と反映（メインセッションで実行）

1. Step 2で残った候補をもとに `AskUserQuestion` ツールで確認を取る。採用候補ごとに「反映先ファイル・変更内容の概要・汎用/プロジェクト固有の判定理由」を提示する。選択肢のラベルは「ファイルパスだけ」や「採用する」のような反映先が分からない書き方にせず、反映先の種別が一目でわかる言い回しを使う
   - agent定義への反映: 「`<agent名>` Agentに反映する」（例:「`code-reviewer` Agentに反映する」）
   - skill本体（SKILL.md）への反映: 「`<skill名>` skillに反映する」（例:「`commit` skillに反映する」）
   - skill内の特定reference・resourceファイルへの反映: 「`<skill名>` skillの`<ファイル名>`に反映する」（例:「`coding-git-workflow` skillの`reference.md`に反映する」）
   - rulesへの反映（無条件ロード）: 「`<ファイル名>` ruleに反映する」（例:「`research.md` ruleに反映する」）
   - rulesへの反映（パス限定）: 「`<ファイル名>` ruleに`paths: <パターン>`指定で反映する」（例:「`coding-go.md` ruleに`paths: **/*.go`指定で反映する」）
   - hookとしての反映: 「`hook-create` スキルでhookを作成して反映する」
   - プロジェクトCLAUDE.mdへの反映: 「`<プロジェクト名>`のCLAUDE.mdに反映する」
   - 新規skill・新規agent作成を提案する場合も、提案する新しい名前を同じ言い回しでラベルに含める（例:「新規skill `<提案名>` を作成して反映する」）
   Step 2で見送った候補も同じタイミングで理由付きで報告し、ユーザーが判定を覆せるようにする。候補が多く1回の質問に収まらない場合は複数回に分けて確認する
2. 承諾された候補のみ、Step 2で整理した変更内容案をもとにファイルを作成・更新する。既存記述の削除・書き換えも、承諾がない限り行わない。hookとしての反映が承諾された場合は、その場で`hook-create`スキルをSkillツールで呼び出す

## Step 4: 反映内容のコミットとpush（メインセッションで実行）

Step 3 でファイルを作成・更新した場合、コミットとpushはユーザーに確認せずそのまま実行する。

保留フラグは、コミットを実行したBashコマンドの作業ディレクトリ（cwd）を基準にリポジトリを判定する。`git -C <path>`で別リポジトリを指定してもcwd自体は変わらないため、add・commit・フラグ解除は対象リポジトリに`cd`した上で同一のBashコマンド呼び出し内で完結させる（`cd <絶対パス> && <コマンド>`。手順ごとに呼び出しを分けると、次のコマンドで元のcwdに戻っている場合がある）。

1. 変更が行われたリポジトリ（`~/.claude` や対象プロジェクト）ごとに、`git add`・`git commit`・保留フラグの解除を1回のBashコマンド呼び出しで連結して実行する（このコミット自体がPostToolUseフックで新たな保留フラグを立て、次のStopで「knowledge-reviewを実行してください」と再度リマインドされるのを防ぐため）
   ```
   cd <リポジトリの絶対パス> && git add <files> && git commit -m "chore: <変更内容の要約>" && ~/.claude/hooks/knowledge-review-flag.sh clear "$(git rev-parse --show-toplevel)" "${CLAUDE_SESSION_ID}"
   ```
2. `git push` を実行する。pushに失敗する場合（リモート未設定・対象ブランチがリモートに存在しない等）はコミットのみ行い、その旨をユーザーに報告する
3. 複数のリポジトリにまたがって反映した場合は、リポジトリごとに1〜2を繰り返す
