# knowledge-review

会話の最初から現在までを振り返り、再利用可能な知見を抽出して適切な場所への反映を提案する。ファイルを先に眺めて「該当がないか探す」のではなく、必ず会話の振り返りから始めること。

Step 1からStep 4までメインセッションで実行する。Copilot CLIのサブエージェントは呼び出し元の会話履歴を継承しないため、会話全体を対象とするStep 1・Step 2を委譲しない。

## Step 0: hookの保留状態を解除する

`knowledge-review-hook` extensionは、このskillの呼び出しを検知した時点で対象セッションの保留状態を解除する。skillからフラグファイルを直接操作しない。そのままStep 1へ進む。

## Step 1: 知見候補の全列挙

この段階では汎用性を判断せず、機械的に拾い上げることに専念する。以下のシグナルごとに該当の有無を1つずつ明示し（該当がない場合も「該当なし」と記す）、該当する出来事を列挙する。

1. ユーザーから受けた指摘・修正・却下（特に同種の指示を2回以上受けたもの）
2. ユーザーが表明した新しい指示・好み（「今後は〜して」のような将来に向けた要望を含む）
3. コマンドやツールの実行が失敗し、別のやり方でリトライした箇所
4. skill の手順どおりに進めて詰まった箇所、手順に書かれていない判断を自分で行った箇所
5. 事前に知っていれば手戻りを防げた発見（環境・ツール・ライブラリの仕様など）
6. 期待した結果と実際の結果が食い違い、原因調査が必要になった箇所
7. うまく機能した工夫・手順で、次回も再現する価値があるもの
8. ユーザーが命名・言い回し・デザインなどについて指摘や誤りの訂正ではなく好みの調整を複数回にわたり繰り返し、最終的な結論に至ったやり取り（結論そのものだけでなく、調整の過程でユーザーが示した判断基準・優先順位に注目する）

各候補は「何が起きたか」「そこから得られる教訓」の1〜2行で書き出す。全シグナルが該当なしの場合はこのスキルを終了する。

## Step 2: 汎用性の判定と反映先の振り分け

各候補に対して次の判定を順に適用する。

1. 一過性の判定: 次のいずれかに該当する候補は反映しない
   - 既存のskill・ruleに問題がなく、その記述どおりに作業が正常完了した場合（結果的に工夫や個別の判断を要したとしても、既存の指示自体が失敗・不足していたわけではない）
   - 今回のセッション固有の外部要因（他セッション・他worktreeとの偶発的な並行作業、その日固有の環境の一時的な不調など）に、既存記述に反することなく即興で対応できた一度きりの事象
   反映候補として次の判定に進めてよいのは、次のいずれかに該当する場合のみとする。
   - 既存の rules・skills の記述どおりに従ったにもかかわらず失敗した（instruction failure。判定3の「特に重要な修正候補」に対応する）
   - 会話や記憶にある限り、同種の状況が複数回発生している（再発性がある）
2. 反映価値の判定: 「次回以降の作業でこの記述を読んだとき、行動が変わるか」で判断する。既に解決済みの個別事象の詳細（修正したバグの原因、そのとき限りの調査結果など）は、記録しても次回の行動を変えないため反映しない。同じ手戻りが再発しうる知見のみ次の判定に進める
3. 既知の判定: 反映先の候補（ユーザーレベルの instructions・skills、対象プロジェクトの CLAUDE.md や `.github/instructions/` 配下）に同じ内容が既に正しく書かれているなら反映しない。既に書かれているが記述が不正確・不足している場合は「既存記述の修正候補」として次の判定に進む
   - 既存の rules・skills の記述どおりに作業して失敗した場合は、特に重要な修正候補として扱う。記述が「常に成り立つ」と断定していて、実際には環境やプロジェクトによって結果が異なると判明したなら、断定を確認手順や条件分岐に置き換える修正を汎用候補として挙げる（例: 「事前ビルドは不要」という断定 → 「デプロイスクリプトにビルドが含まれるか確認し、含まれない場合は先にビルドする」）。プロジェクト側への例外注記だけで済ませると、別のプロジェクトで同じ失敗が再発する
4. 汎用性の判定: 別のリポジトリ・別のプロジェクトで同じ作業をしても、この知見がそのまま成立するかを判定する
   - 特定のプロジェクト名・社内サービス名・リポジトリ内のファイルパスなどの固有名詞を使わないと教訓を記述できないならプロジェクト固有
   - 固有名詞なしで書ける場合でも、組織・チーム固有の運用ルール（コミットメッセージへのチケットID付与など）はプロジェクト固有として扱う
   - ツールに関する知見は「ツール自体の一般的な性質」（例: git stash は untracked ファイルを対象にしない）なら汎用、「そのプロジェクトでのツールの運用」（例: このリポジトリでは pnpm を使う）ならプロジェクト固有
   - 迷った場合は「6ヶ月後に無関係なプロジェクトでこの記述を読んで役に立つか」で判断し、それでも迷うならプロジェクト固有として扱う
5. 抽象化の検討: プロジェクト固有と判定した候補についても、一段抽象化すると汎用的な教訓にならないかを検討する（例: 「このリポジトリは pnpm を使う」という固有の知見 → 「パッケージを追加する前に lockfile の種類でパッケージマネージャを確認する」という汎用の手順）。抽出できた教訓は独立した候補として追加し、判定1から同じようにかけ直す。プロジェクト固有の失敗は汎用手順の確認不足を露呈していることが多く、固有の知見をプロジェクトに記録するだけではその改善機会を逃す
6. 反映先の決定:
   - 汎用かつ特定の作業手順に関するもの: 該当する `~/.copilot/skills/` のスキル。手順が長い・特定の観点に限定される場合はSKILL.md本文ではなく `references/` 配下の個別ファイルに反映することも検討する（既存の分割方針に倣う）。既存スキルに適切な反映先がなければ、新規スキル作成を検討する。新設する場合は `~/.copilot/skills/` 配下の既存スキルのディレクトリ構成・命名規則（ケバブケースの名称、`SKILL.md` のfrontmatter形式など）に倣う
   - 汎用かつ作業全般で常に守るべき制約・スタイル: `~/.copilot/instructions/`（適切なファイルがなければ新規作成を提案する）
   - 特定のagentのペルソナ・振る舞い・出力フォーマットに関するもの: `~/.copilot/agents/<name>.md`（またはプロジェクトの `.github/agents/<name>.md`）本体
   - プロジェクト固有: 対象プロジェクトの既存instructionファイル。適切なファイルがなければCLAUDE.md、AGENTS.md、`.github/instructions/<name>.instructions.md`の順で新規作成を検討する。ユーザーレベルには入れない
   - 作業対象が `~/.copilot` 自体である場合は、instructions・skills・agents本体への反映として扱う

## Step 3: ユーザー確認と反映（メインセッションで実行）

1. Step 2で残った候補をもとに `ask_user` ツールで確認を取る。採用候補ごとに「反映先ファイル・変更内容の概要・汎用/プロジェクト固有の判定理由」を提示する。選択肢のラベルは「ファイルパスだけ」や「採用する」のような反映先が分からない書き方にせず、反映先の種別が一目でわかる言い回しを使う
   - agent定義への反映: 「`<agent名>` Agentに反映する」（例:「`code-reviewer` Agentに反映する」）
   - skill本体（SKILL.md）への反映: 「`<skill名>` skillに反映する」（例:「`commit` skillに反映する」）
   - skill内の特定reference・resourceファイルへの反映: 「`<skill名>` skillの`<ファイル名>`に反映する」（例:「`coding-git-workflow` skillの`reference.md`に反映する」）
   - rulesへの反映: 「`<ファイル名>` ruleに反映する」（例:「`research.md` ruleに反映する」）
   - プロジェクトCLAUDE.mdへの反映: 「`<プロジェクト名>`のCLAUDE.mdに反映する」
   - 新規skill・新規agent作成を提案する場合も、提案する新しい名前を同じ言い回しでラベルに含める（例:「新規skill `<提案名>` を作成して反映する」）
   Step 2で見送った候補も同じタイミングで理由付きで報告し、ユーザーが判定を覆せるようにする。候補が多く1回の質問に収まらない場合は複数回に分けて確認する
2. 承諾された候補のみ、Step 2で整理した変更内容案をもとにファイルを作成・更新する。既存記述の削除・書き換えも、承諾がない限り行わない

## Step 4: 反映内容のコミットとpush（メインセッションで実行）

Step 3 でファイルを作成・更新した場合、コミットとpushはユーザーに確認せずそのまま実行する。

1. 変更が行われたリポジトリ（`~/.copilot` や対象プロジェクト）ごとに、反映で変更したファイルのみを `git add <files>` でステージする
2. `chore: <変更内容の要約>` の形式で日本語のコミットメッセージを作成し `git commit` する
3. `git push` を実行する。pushに失敗する場合（リモート未設定・対象ブランチがリモートに存在しない等）はコミットのみ行い、その旨をユーザーに報告する
4. 複数のリポジトリにまたがって反映した場合は、リポジトリごとに1〜3を繰り返す。`knowledge-review-hook` extensionはskill実行中のコミットを保留対象にしないため、skillからフラグを再解除しない

## 完了処理: 保留フラグの解除（メインセッションのみが実行する）

Step 0でextensionが解除済み。追加の操作は不要。
