# 動作の正しさに関する規約(デグレ・要件網羅性)

## 前提

coding-architectureとcoding-standardsは、コードの内部構造・書き方・シンボル参照の妥当性を検証する規約である。これらはコードそのものを読めば違反を検出できる。

本スキルはそれとは異なる軸で、「変更後のコードが実際にどう動くか」を要件と既存動作の両面から検証する。

- 要件網羅性: 変更が、要求された振る舞い・受け入れ条件を漏れなく満たしているか
- デグレ: 変更が、これまで動いていた既存の振る舞いを壊していないか

いずれも、変更差分のコードだけを読んでいても気づけない。要件文書（issue・Notionタスク・PR本文の受け入れ条件）と、変更対象の機能に実際に到達しうる利用シナリオを起点に、コードがそれをどう扱うかを逆算して確認する必要がある。要件文書や到達経路の情報が指摘の中で示されていない場合、それらを確認せずに「問題なし」と判断しない。

## 要件網羅性の観点

| アンチパターン | 検出の観点 | 解消方法 |
| --- | --- | --- |
| 受け入れ条件の部分対応 | タスク・issue・PR本文に列挙された受け入れ条件・制約のうち、実装が満たしていない項目がある | 受け入れ条件を1件ずつ実装のどこが満たしているかと対応付け、対応箇所が見つからない項目を洗い出す |
| 明記されたエッジケースの欠落 | 要件文書に明記された特殊ケース・例外条件（空文字、0件、権限なし、未認証など）に対応する分岐が実装に存在しない | 要件文書に記載されたエッジケースを1件ずつ実装の分岐と対応付ける |
| 既知の不整合の自己判断による見送り | 実装者自身が気づいた要件との不整合や回帰を、優先度を自己判断して「別チケット」「スコープ外」「優先度低」として片付けている | 見送りは実装者の裁量で完結させず、要件確定者（レビュアー・ユーザー）の明示的な承認を要する。承認の記録が無い見送りは未対応の指摘として扱う |
| 設計判断と実装の不一致 | 設計文書・仕様書で決めた前提（既存の仕組みに相乗りするか個別に持つか、使用する設定値、URL・パス・パラメータの組み立て方など）が実装と食い違っている。特に「既存の共有部分に相乗りし、専用部分だけコード側で補う」という設計の場合、補うべき専用部分の実装漏れ | 設計文書に記載された判断事項を1件ずつ実装の該当箇所と対応付け、値・組み立て方・補うべき専用処理が一致しているか確認する |

## デグレの観点

| アンチパターン | 検出の観点 | 解消方法 |
| --- | --- | --- |
| 到達経路の見落とし | 変更対象の機能・画面に到達する経路（通常のUI操作、直リンク・共有URL、外部サイトからの流入、別クライアント、権限の異なるユーザーなど）を1種類しか想定せず、他の経路での挙動を検証していない | 変更対象への到達経路を列挙し、各経路で変更後も期待通りに動作するかを個別に確認する |
| 分岐・早期リターンの意図しない拡大縮小 | 分岐条件や早期リターンの条件を変更した際、その条件変更が対象外だったケースにも影響していないか未確認 | 変更前後で「その分岐に入る/入らないケースの集合」を比較し、意図しないケースが混入・脱落していないか確認する |
| 除去された処理の影響漏れ | 既存のガード・フォールバック・分岐を削除する変更で、その処理が防いでいた別のケースが再び発生しうる状態に戻っていないか未確認 | 削除した処理が「何を防ぐために存在していたか」をコミット履歴やコメントから確認し、その目的が別の手段で維持されているかを検証する |
| テストで固定されていない振る舞い変更 | 既存の振る舞いを変更したにもかかわらず、その変更後の振る舞いを固定するテストが無い | 変更後の振る舞いを明示するテストケースを追加し、将来の再回帰を検知できるようにする |
| 検知力のない疑似テスト | テストは存在するが、モック・スタブが実装からの入力（リクエストのパス・メソッド・ボディなど）を検証せず常に固定の結果を返すなど、対象の実装が壊れても失敗しない | モック・スタブが実装からの実際の入力を検証しているか確認する。テストケース名が示すエラー型・分岐と、モックが返す型・期待値が一致しているかも確認する |
| 実行環境依存の前提 | タイムゾーン・文字コード/照合順序・接続数上限・タイムアウトなど、実行環境（dev/stg/prodなど）によって値が異なりうる前提を、特定の環境の値に固定して実装している | 日付境界計算のタイムゾーン、文字コード/照合順序、環境ごとに変わりうる値が環境変数化されているかを洗い出し、環境が変わっても成立するか確認する |

## 検出の進め方

1. 要件文書を特定する。呼び出し元からPR番号・issue番号・NotionページのURLやIDのいずれかが伝えられている場合、次の方法で自分から取得する
   - PR番号: `gh pr view <PR番号> --json body --jq .body` でPR本文（受け入れ条件を含む場合が多い）を取得する
   - issue番号: `gh issue view <issue番号>` でissue本文・コメントを取得する
   - NotionページのURL/ID: Notion MCPで本文を取得する
   - いずれの識別子も伝えられていない、または取得に失敗した場合はエラーとする。要件文書が無ければ要件網羅性を検証できず、確認したことにならないまま「問題なし」と報告してしまう方が実害が大きい。この場合、以降の検出手順（2〜5）を実行せず、ReportFindingsで次の1件のみを必須修正として報告して終了する: `category: "blocked-missing-requirements"`, `summary: "要件文書が特定できずレビューを実施できない"`, `failure_scenario`に不足している識別子（PR番号/issue番号/NotionページURL）と、呼び出し元がそれを渡していない旨を明記する
2. 要件文書から受け入れ条件・制約・既知のエッジケースを列挙する
3. 列挙した各項目に対応する実装箇所を特定する。対応箇所が無い項目、またはPR本文で「別チケット」「優先度低」等として先送りにされている項目を必須修正として指摘する
4. 変更対象のファイル・関数の呼び出し元・利用シナリオを洗い出す。特に「この画面・機能にどうやって到達するか」を複数パターン列挙し、変更前後でその経路の動作が変わっていないかを確認する。この観点は要件文書の有無に関わらず必ず実施する
5. 変更差分（diff）の追加・削除行だけでなく、変更前のコードとの振る舞いの差分（除去された分岐、変更されたデフォルト値、変更された条件式）を意識して読む
