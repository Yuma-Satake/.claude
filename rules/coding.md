# Codingの基本

## コメントの書き方

重要な前提：コメントはコード自体と同じぐらい重要なものです。以下のルールを無視し、これを軽視することはコード品質の低下を受け入れるのと同様です

- 後続で対応するとした箇所については、チケットの内容を`TODO: {title} ({url})` の形式でコメントを残すこと
- コードを編集する際、変更内容を説明するコメントを絶対に追加せず、必要な説明は会話の中で行うこと。コード上にはコードのみで伝わらない設計意図などを記述すること
- コードの変更を行った場合には、付属したコメントも更新することを徹底する。該当箇所のみならず、`/docs`のような箇所や、そのコードを参照している箇所でも影響がある場合があるので、探して更新すること
- ある処理（nilを返す、早期リターンする等）の理由を説明するコメントは、その処理を実際に行う箇所の真上に書くこと。プロパティ宣言やドキュメンテーションコメントなど、実際の処理から離れた場所に書くと、処理の実装が変わってもコメントだけ古いまま取り残されやすい
- 処理の理由を説明するコメントであっても、複数行にわたる詳細な経緯（発見した不具合の内容、検討した代替実装との比較、パターンの由来など）は書かないこと。目的・理由は1行程度に圧縮し、詳しい経緯はコミットメッセージやPR本文に記載する
- if・guardの分岐条件や判定用ヘルパー関数が表す具体的な条件（「AかつB」「AまたはB」等）を、コメントで文章化して繰り返さないこと。条件はコード自体が唯一の正であり、それをコメントとして書き起こすとコードとコメントの二重管理になる。条件を変更した際にコメントの更新が漏れると、実装と矛盾したコメントが残り続ける。コメントは判定の目的・意図に留める
- 1行で完結するコメントの末尾に句点（。）を付けないこと
- コメントはコードに永続的に残るものであるため、現在対応中のissueやPRに紐づく一時的な状況・スコープを記載しないこと（例:「本issueのスコープでは○○は使わない」）。恒久的に成り立つ事実のみを書く
- ドキュメンテーションコメント（Swiftの`///`、JSDocの`/** */`等）を持つ宣言にTODO等の付随コメントを追加する際は、ドキュメンテーションコメントと宣言の間に挟まない。ドキュメンテーションコメントより前に置く（挟むとドキュメンテーションコメントが宣言から分離した扱いになり、静的解析で警告・エラーになる言語がある）
- コメント中でissueやPRを参照する場合（例:「issue #100の設計を踏襲」）、番号ではなくURLを記載すること。番号だけではリポジトリを跨いで参照した際に対象を一意に特定できない
- コメントにその宣言の使用箇所・呼び出し元を書かないこと（例:「◯◯と△△の両ドメインで使う共有実装」「Widgetから利用する」「Homeのみが利用する」）。依存関係は後から増減するため、書いた時点の呼び出し元は容易に事実と食い違う。書くのはその宣言自体が何であるか・何を保証するか（例:「HealthKit非依存」）に留める
- コメントに「純粋関数」「イミュータブル」などの実装特性を書かないこと。何を処理する関数かのみを書く（例:「サンプルを暦日ごとに合算する純粋関数」ではなく「サンプルを暦日ごとに合算する」）
- 複数行にわたるコメントを書く際、テキストの長さ（桁数）を意識した位置で改行しないこと。改行は文章の終わり（文末）でのみ行う
- 1箇所に複数のコメント（複数の異なる指摘・理由・注意点など）を書く場合は、箇条書きにすること。地続きの文章として並べない
